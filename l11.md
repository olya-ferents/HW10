# L11 — журнал кроків

## Навіщо ця лабораторна

Ви перевіряєте, чи можна довіряти тестам асистента: кладете їх поруч зі своїми ручними й проганяєте обидва набори на тому самому списку мутантів.

## Мета

Для `app/engines/fx.py` отримати mutation score ручного, згенерованого й об'єднаного наборів та назвати клас мутантів, у якому кожен набір слабший. Лабораторна охоплює три результати навчання:

- **Базове порівняння:** baseline, список мутантів, генерація з покриттям і прогін мутантів (кроки 1, 2, 4, 6) — false coverage та вцілілий мутант.
- **Критерії рев'ю:** критерії й промпт, рев'ю з журналом (кроки 3, 5).
- **Вимірювання впливу:** baseline, генерація, рев'ю й прогін мутантів (кроки 1, 4, 5, 6) — хвилини для розрахунку ціни у двох валютах і число для звіту. Ціну й Impact Report повністю опрацьовуєте в ДЗ.

## Що маєте побачити загалом

- На кроці «Згенерувати набір і зняти покриття» згенерований набір має дати помітно вище рядкове покриття, ніж ручний. На еталонному прогоні під Python 3.14 результат — 100 % проти 64 %.
- На кроці «Прогнати мутантів на трьох наборах» картина змінюється: mutation score згенерованого набору зазвичай не вищий за ручний, а сліпі зони наборів лежать у різних класах.
- Об'єднаний набір зазвичай ловить більше мутантів, ніж кожен окремо. Часто один клас мутантів виживає в обох наборах.

## Артефакти

- `tests/manual/` — 5–8 тестових функцій ручного baseline із зафіксованим часом.
- `mutants.toml` — список із 12 мутантів, закомічений до генерації й першого прогону.
- `prompts/review-criteria.md` і `prompts/generation-prompt.md` — шість критеріїв рев'ю та промпт, закомічені до генерації.
- `tests/generated/`, `reports/generation.json` і показники рядкового покриття обох наборів.
- Журнал рев'ю з рішенням щодо кожного згенерованого тесту; відхилені тести, переписані людиною, — у `tests/rewritten/`.
- `reports/mutants-*.json` і таблиця результатів за чотирма класами мутантів та трьома наборами: ручним, згенерованим і об'єднаним.
- Усі результати лабораторної заповнюються в `ai-adoption-impact-report.template.md` у корені кіта.
- У ДЗ шаблон доповнюється ціною у двох валютах і сімома рядками Impact Report; фінальний звіт зберігається як `ai-adoption-impact-report.md`.

## Що входить у заняття та важливі обмеження

- Кіт `paypilot-l11-eval` містить знімок `app/engines/fx.py` і таблицю тарифів `app/engines/policy.py` зі стенду, каталоги тестів, приклад `mutants.example.toml`, скрипт `tools/run_mutants.py` і налаштування асистента `.claude/settings.json`.
- Стенд PayPilot запускати не потрібно: тести й мутанти працюють із кодом у кіті, а не торкаються стенду.
- `agent-prompt/` — довідковий приклад методу для промпту агента; для лабораторної та ДЗ він не потрібен. Критерії лабораторної пишуться самостійно в `prompts/`.
- Наслідок дефекту `D20` для цієї теми студент відтворює мутантом `A-01` класу «значення тіру»; оригінальний код модуля не змінюється.
- Для генерації в інструкціях кіта використовується Claude Code із ключем `ANTHROPIC_API_KEY` та моделлю Sonnet; підписка не потрібна.
- Референсні набори лабораторної (ручний і згенерований), список мутантів і вивід генерації є у ментора. Якщо генерація або прогін не вдалися, повідомити ментора в чаті курсу.

## Периметр коду та межі доступу асистента

У L10 ви розбирали периметр даних. Тепер за цю межу йде код: асистент бачить логіку й структуру `app/engines/fx.py` та ваші коментарі. Не давайте йому змінювати еталони: модуль, таблицю тарифів, ручний набір і список мутантів. Якщо асистент підлаштує еталон під власний результат, порівняння втратить сенс.

У цьому кіті межі доступу налаштовані у `.claude/settings.json`: асистент може читати модуль, але не може редагувати файли `app/` чи `tests/manual/`, `mutants.toml` і `prompts/`. Він також не може прочитати таблицю тарифів, ручний набір, список мутантів і критерії рев'ю, щоб генерація не підглядала в матеріали для незалежної перевірки. Перш ніж натиснути Enter, з'ясуйте, куди саме йде ваш репозиторій: периметр коду — таке саме питання відповідальності, як і периметр даних.

## Кроки лабораторної

### Перед кроком 1: віртуальне оточення

Виконайте команди з кореня репозиторію в одному терміналі. Оберіть лише блок для своєї системи; не запускайте всі три.

macOS / Linux / WSL:

```bash
python3 -m venv .venv &&
source .venv/bin/activate &&
python -m pip install -r requirements.txt
```

На macOS до активації використовуйте `python3`: команда `python` може бути відсутня. `&&` не дає перейти до наступного кроку, якщо попередній завершився помилкою. Після активації `python` указує на Python віртуального оточення.

Git Bash на Windows:

```bash
python -m venv .venv
source .venv/Scripts/activate
pip install -r requirements.txt
```

Windows PowerShell:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Переконайтеся, що віртуальне оточення активоване перед встановленням залежностей. Якщо PowerShell блокує `Activate.ps1`, інструкція з виправлення є в [README.md](./README.md).

### Перед генерацією: ключ асистента

Задайте `ANTHROPIC_API_KEY` у тому самому терміналі, де запускатимете генерацію Claude Code. Файл `.env` стенду асистент не читає. Оберіть лише команду для своєї оболонки та замініть `ВАШ_КЛЮЧ` власним ключем.

macOS / Linux / WSL / Git Bash:

```bash
export ANTHROPIC_API_KEY="ВАШ_КЛЮЧ"
```

Windows PowerShell:

```powershell
$env:ANTHROPIC_API_KEY="ВАШ_КЛЮЧ"
```

Не надсилайте ключ у чат, не записуйте його в цей журнал і не комітьте. Команда з ключем може зберегтися в історії термінала. У новому терміналі змінну потрібно задати знову.

### Перевірка підготовки та копія звіту

**4. Перевірте запуск pytest** в активованому віртуальному оточенні:

```bash
pytest tests/manual
```

До написання ручних тестів очікується `no tests ran`: тести ще відсутні, це нормально. pytest у цьому випадку повертає код 5, тому наступну команду виконуйте окремо, не через `&&`. Якщо результат інший, звіртеся з типовими помилками № 5 і 7 матеріалів заняття.

**5. Створіть власну копію звіту** (лише якщо її ще немає, щоб не перезаписати внесені результати).

macOS / Linux / WSL / Git Bash:

```bash
cp ai-adoption-impact-report.template.md ai-adoption-impact-report.md
```

Windows PowerShell:

```powershell
Copy-Item ai-adoption-impact-report.template.md ai-adoption-impact-report.md
```

До першого власного коміту виконайте:

```bash

```

У шапці [ai-adoption-impact-report.md](./ai-adoption-impact-report.md) замініть підказку після **Коміт кіта:** отриманим значенням. На момент підготовки інструкції перевірене значення — `d6c471a`.

До написання baseline заповніть колонку «Прогноз» у [звіті](./ai-adoption-impact-report.md#прогноз-перед-кроком-1):

Прогнозуйте за чотирма класами: `значення тіру`, `межа EUR 1 000`, `арифметика`, `форма результату` — по три мутанти в кожному. Теоретичні результати отримано на еталонному списку; свій список ви складете на кроці 2.

Колонку «Виміряно» та висновок про найбільшу розбіжність заповнюйте після кроку 6. Початковий прогноз не підганяйте під результат: розбіжність цікавіша за самі числа.

### Крок 1: написати ручний baseline за 40 хвилин

**Навіщо:** отримати прилад-опору для порівняння — власний набір із відомою ціною, написаний до перегляду згенерованого коду.

1. Увімкніть таймер і запишіть час старту в розділ 1 [звіту](./ai-adoption-impact-report.md).
2. Відкрийте [test_fx_manual.py](./tests/manual/test_fx_manual.py): у заготовці є імпорт модуля й підказка із сигнатурою `fx.quote`.
3. Самостійно, без асистента, напишіть 5–8 тестових функцій на `fx.quote`. Параметризований тест рахується як одна функція.
4. Очікувані значення беріть із [таблиці тарифів](./app/engines/policy.py), не з виводу функції. Записуйте конкретні числа в assertion, наприклад `assert q.spread_pct == 0.9`.
5. Запустіть набір на оригінальному модулі:

   ```bash
   pytest tests/manual
   ```

6. Зупиніть таймер. Запишіть час фінішу й фактичну кількість хвилин у розділ 1 звіту, навіть якщо вийшло більше ніж 40.
7. Після успішного прогону закомітьте набір, виконуючи команди окремо:

   ```bash
   git add tests/manual
   git commit -m "L11: ручний baseline"
   ```

8. Отримайте SHA коміту й запишіть його в поле «Коміт набору» розділу 1:

   ```bash

   ```

**Очікуваний результат:** `N passed`, 5–8 тестових функцій, SHA коміту та фактичний час у звіті. Через параметризацію число `passed` може перевищувати кількість функцій. `no tests ran` після написання baseline вже не є очікуваним результатом.

**Якщо тест падає на оригіналі:** перевірте очікуване за таблицею тарифів і чи перевищує сума ліміт тіру. Не підганяйте очікуване під вивід функції. Див. типову помилку № 2 матеріалів заняття.

**Ціна:** без викликів моделі під час написання baseline; людський час записується фактично, а не як планові 40 хв. У ДЗ ці дані йдуть у розділ 1 і рядок «Час людини на написання» розділу «Ціна у двох валютах» (критерії 1 «Baseline» і 5 «Ціна»).

**На іншому проєкті:** до підключення асистента до модуля виміряйте, скільки хвилин займає написання тестів руками.

### Крок 2: скласти й зафіксувати список мутантів

**Навіщо:** створити незмінну мірку для всіх трьох наборів. Список, складений після прогону, підганяє вимірювання під результат. Мутант — копія модуля з однією маленькою навмисною зміною; клас мутанта — група змін одного типу.

1. Скопіюйте [зразок](./mutants.example.toml) у `mutants.toml`, якщо власного списку ще немає. Не перезаписуйте вже внесену роботу.

   macOS / Linux / WSL / Git Bash:

   ```bash
   cp mutants.example.toml mutants.toml
   ```

   Windows PowerShell:

   ```powershell
   Copy-Item mutants.example.toml mutants.toml
   ```

2. Залиште готовий `A-01` і допишіть ще 11 мутантів: по три на кожен клас. Поле `class` пишіть дослівно:

   | Значення `class` | Приклад зміни |
   | --- | --- |
   | `значення тіру` | Спред `tier2`: `0.9` → `1.5` у [policy.py](./app/engines/policy.py) |
   | `межа EUR 1 000` | `<=` → `<` у рядку `within = …` у [fx.py](./app/engines/fx.py) |
   | `арифметика` | Помилка в обчисленні спреду або курсу |
   | `форма результату` | Рядок замість числа в `as_dict()` або хибне поле котирування |

3. У `find` скопіюйте фрагмент коду дослівно, з усіма пробілами. Він має зустрічатися у вибраному файлі рівно один раз. Зміну задавайте в `replace`, не редагуючи оригінальний модуль.
4. Перевірте застосовність списку без прогону тестів на мутантах:

   ```bash
   python tools/run_mutants.py --check
   ```

5. Переконайтеся, що є 12 мутантів, по три в кожному класі, й закомітьте список до генерації та першого прогону:

   ```bash
   git add mutants.toml
   git commit -m "L11: список мутантів"
   ```

6. Після фіксації список не змінюйте. Запишіть список, SHA й дату коміту в розділ 2 [звіту](./ai-adoption-impact-report.md). Коміт можна переглянути командою:

   ```bash
   git log -1 --format="%h %aI" -- mutants.toml
   ```

**Очікуваний результат перевірки за матеріалами заняття:** `Список mutants.toml: 12 мутантів, кожен застосовується до коду рівно в одному місці.` По три мутанти в кожному з чотирьох класів. Після коміту попередження про незакомічений список зникає.

**Якщо перевірка не проходить:**

- `find` знайдено 0 разів — заново скопіюйте фрагмент із вихідного файлу дослівно (типова помилка № 1).
- Немає трьох мутантів у кожному з чотирьох класів — перевірте кількість записів і точне написання `class`.
- Бракує ідей — розгляньте зміну знака порівняння (`>` → `>=`) або арифметичної операції (`+` → `-`) у частині коду, що відповідає класу.

**Ціна за планом заняття:** без викликів моделі для складання списку. Якщо користуєтеся допомогою AI, зазначте її у звіті.

**У ДЗ:** розділ 2 звіту, критерій 2 «Незмінний набір» — список закомічено раніше за перший прогін.

**На іншому проєкті:** до порівняння двох наборів тестів зафіксуйте й закомітьте спільний список мутантів.

**Навіщо:** побачити перевагу рядкового покриття на власних даних до того, як мутанти перевірять якість assertion. Рядкове покриття — частка виконаних рядків модуля.

**Фіксація початкового набору:** після перевірок закомітьте його як є разом із результатом генерації:

### Крок 5: відрев'ювати згенеровані тести з журналом

**Навіщо:** пропустити кожен тест через людський фільтр і записати ціну кожного рішення.

1. Увімкніть таймер рев'ю. Час на переписування рахуйте окремо.
2. Відкрийте [згенерований набір](./tests/generated/test_fx_generated.py) і розділ 5 [звіту](./ai-adoption-impact-report.md). Пронумеруйте функції в журналі за порядком: `G-01`…`G-23`. Параметризований тест — один запис; сам файл тестів для нумерації не змінюйте.
3. Кожній функції поставте `accepted` або `rejected`, зокрема тим, які приймаєте без змін.
4. Для кожної запишіть критерій і причину за зафіксованими [критеріями](./prompts/review-criteria.md). Для тестів на винятки й властивості не застосовуйте «Оракул».
5. Відхилений тест, який варто зберегти, перепишіть вручну в `tests/rewritten/test_fx_rewritten.py`. У журналі вкажіть дію, наприклад «переписано вручну як R-01 у tests/rewritten/».
6. Якщо є переписані тести, перевірте їх на оригінальному модулі:

   ```bash
   pytest tests/rewritten
   ```

7. Зелені переписані тести закомітьте:

   ```bash
   git add tests/rewritten
   git commit -m "L11: переписані тести"
   ```

8. Підсумуйте в розділі 5 кількість прийнятих, відхилених і переписаних тестів, причини відхилення та окремі суми хвилин. Перенесіть час у рядки «рев'ю й відбір» і «переписування відхиленого» розділу 7.

Формат запису для кожної функції:

```text
id: G-01
verdict: <accepted або rejected>
criterion: <критерій або —>
reason: <причина рішення>
action: <прийнято як є / відхилено / переписано вручну як R-…>
minutes: <фактичний час рев'ю> + <фактичний час переписування, якщо було>
```

**Згенерований файл не змінюйте:** на кроці 6 вимірюється початковий набір асистента. Виняток із матеріалів заняття — видалення тестів, червоних на оригіналі, окремим комітом зі збереженням відхилення в журналі. У нашому прогоні всі 23 тести зелені, тому цей виняток не потрібен.

**Очікуваний результат:** 23 записи в журналі, а не лише список відхилених. Прийняті тести мають показати нові класи входів або перевірки, яких бракує ручному набору.

**Якщо критерію бракує:** опишіть причину словами й позначте прогалину. Не змінюйте таблицю критеріїв заднім числом.

**Ціна за планом заняття:** людське рев'ю й ручне переписування без викликів моделі. Якщо залучаєте AI, задекларуйте допомогу; його роботу не видавайте за власне людське рев'ю.

**У ДЗ:** розділ 5 і відповідні рядки часу в розділі 7, критерії 3 «Журнал рев'ю» і 5 «Ціна».

**На іншому проєкті:** ведіть у PR журнал рішень про згенерований код: вердикт, критерій, хвилини.

### Крок 6: прогнати мутантів на трьох наборах

**Навіщо:** отримати mutation score та розбивку за класами, визначити слабші класи кожного набору. Mutation score — кількість вбитих мутантів, поділена на 12.

1. Із кореня кіта в активованому оточенні послідовно запустіть той самий незмінний список:

   ```bash
   python tools/run_mutants.py --set manual
   python tools/run_mutants.py --set generated
   python tools/run_mutants.py --set all
   ```

   Дочекайтеся завершення кожної команди. `all` — ручний плюс початковий згенерований набір; переписані тести не входять.

2. Збережіть звіти прогонів у git:

   ```bash
   git add reports
   git commit -m "L11: прогони мутантів"
   ```

3. У розділі 6 [звіту](./ai-adoption-impact-report.md) для кожного набору запишіть:
   - шлях до JSON-звіту;
   - кількість вбитих із трьох у кожному класі;
   - загальну кількість вбитих із 12 і mutation score;
   - усі ID з рядка `Вцілілі:`, не лише відсоток.
4. Одним реченням назвіть слабший клас кожного набору й мутантів, які вижили в обох.
5. Поверніться до прогнозу перед кроком 1: заповніть колонку «Виміряно» й поясніть найбільшу розбіжність, не змінюючи початкові припущення.

### Розібраний кейс: як прочитати один згенерований тест

Навчальний схематичний приклад зі скриншота, не результат вашої генерації. У вашому наборі під номером `G-07` може бути інший тест. Такий розбір виконуєте для кожного тесту на кроці 5.

| Що | Значення у прикладі | Як читати |
| --- | --- | --- |
| Тест | `G-07`, `test_quote_returns_amount` | Ім'я не називає правило, яке перевіряється: критерій «Ім'я». |
| Вхід | `fx.quote(1200, "EUR", "USD", "tier2")` | Для `tier2` сума понад ліміт EUR 1 000, тож має застосуватися спред 0.9 %. |
| Assertion'и | `isinstance(q.final_amount, float)`, `q.final_amount > 0` | Перевіряють форму й знак, але не конкретне значення: критерій «Рівень assertion». |
| Звідки очікуване | Нізвідки: тест не порівнює з тарифами. | Очікуваного немає, тож «Оракулу» немає що оцінювати; вирішує «Рівень assertion». |
| Мутант `A-01`: спред `tier2` 0.9 → 1.5 | Тест лишається зеленим. | Мутант вижив: тест сліпий до значення спреду. |
| Вердикт у журналі | `rejected`; критерій «Рівень assertion»; дія: переписано вручну як `R-01` у `tests/rewritten/`; 1 + 2 хв | Час враховується окремо як «рев'ю й відбір» та «переписування». Це числа прикладу, не ваш вимір. |
| Висновок | Тест виконує рядки, але не перевіряє правильність розрахунку. | Це false coverage на одному тесті. |

## Терміни теми

| Термін | Що означає |
| --- | --- |
| Ручний baseline | Набір із 5–8 тестових функцій для одного модуля, написаний вручну із засіченим часом до перегляду згенерованого коду. Це прилад-опора для порівняння з асистентом. |
| [tests/manual/](./tests/manual/) | Каталог вашого ручного набору. |
| [tests/generated/](./tests/generated/) | Каталог набору, який пише асистент. |
| [tests/rewritten/](./tests/rewritten/) | Каталог тестів, які ви переписали з відхилених; у три набори кроку 6 не входить. |
| Об'єднаний набір | Ручний і згенерований набори, прогнані разом: `--set all`. Переписані тести не додаються. |
| `--set` | Вибір набору для прогону мутантів: `manual`, `generated` або `all`. |
| `mutants.toml` | Ваш список із 12 мутантів, по три на клас; після фіксації на кроці 2 не змінюється. |
| Рядкове покриття (line coverage) | Частка рядків модуля, виконаних під час прогону тестів; число з `pytest --cov=app.engines.fx`. Показує, що рядок виконався, але не чи перевірено результат. |
| False coverage | Рядки виконуються, але перевірка не порівнює результат із незалежним очікуваним: assertion відсутній, перевіряє лише форму або очікуване взято з того самого коду. Покриття зростає, а здатність ловити дефекти — ні. |
| Мутант (вбитий / вцілілий) | Копія модуля з однією навмисною зміною зі списку кроку 2, наприклад `0.9` → `1.5`, `>` → `>=` або `+` → `-`; скрипт створює її в тимчасовій папці. Мутант вбитий, якщо на ньому падає хоча б один тест; вцілілий, якщо всі тести зелені. |
| Mutation score | Частка вбитих мутантів від усіх внесених; у цій лабораторній — кількість вбитих, поділена на 12. |
| Клас мутанта | Група мутантів одного типу. У лабораторній чотири класи по три мутанти: `значення тіру`, `межа EUR 1 000`, `арифметика`, `форма результату`. |
| `monkeypatch` | Засіб pytest для тимчасової підміни змінної модуля; тут — таблиці тарифів. |
